## 一、结论摘要

**数据看板处于「静态原型」状态：后端 0% 、前端为带完整 UI 骨架的假数据页。** 模块未开工（v1.1 的 DB1~DB5 均未启动），因此本报告不评"开发缺陷"，而是评**现状风险**与**开工前必须知道的事实**。核心风险一条：

> **「演示」标注已被移除（提交 8797869），但数据仍是写死的假数字**——用户会把它当真实数据看。当前状态比带"演示"标注时更具误导性，构成上线门禁：DB4 完成前必须隐藏 `/analytics` 入口。

| v1.1 任务 | 现状 | 差距 |
|---|---|---|
| DB1 数据层与导入（3 表 + CSV） | 表未建（schema.ts 无 metric 类表）；无 CSV 依赖（Q8 已拍板引入 papaparse） | 全新建 |

## 二、现状缺陷清单（按上线影响排序）

- 影响：登录即可见（DB7 说登录可见全量），假数字无"演示"提示直接呈现。

**P0-D2 无 loading / empty / error 三态。**
- 证据：三态计数 0/0/0（全站唯一）；数据是同步 const，无任何请求。
- 影响：接真后若不补三态，慢查询时白屏、空数据时无引导。
- 处置：DB4 必含（v1.1 已写入 AC-M13：空态文案「发布首批内容并导入 CSV 回采数据」）。

## 三、后端数据层核实（开工前置事实）

1. **回采锚点完好**：`publish_log.external_video_id`(vc64) / `video_url` / `finished_at` 在 `schema.ts:1204-1208`——CSV 两级匹配与窗口扫描的锚点可直接用。
2. **`metrics` 模块保留不动**：现有 `GET /api-calls(/summary)` 是 FR-C4 成本记录（`modules/metrics/routes.ts`），与看板无耦合；新接口建 `modules/analytics/`。前端 `api/cost.ts` 的 summary 调用可选用于看板页头成本卡（复用现成接口，不新增后端工作）。
3. **`TopicSource` 与状态机**：`topics/repo.ts:7` 枚举需加 `'data_backfeed'`；`assertTransition`(:73) 按 source 分规则——data_backfeed 必须走 news 同款（candidate→assigned→sent），不可走 benchmark 的"创建即 sent"（D8 口径）。这是 v1.1 相对 v1.0 修正的关键契约点。
4. **调度与上传先例充分**：news 15min repeat（`news/jobs.ts`）、multipart 直传+settle 收口（`personas/routes.ts:168-195`）、`QUEUE_NAMES` 注册——DB1/DB2 全部有仓内范式可抄，无技术不确定性。
5. **风险确认**：无。该模块全部为新建（3 新表可 DROP 回滚、新模块、新队列），对既有模块的唯一侵入是 copy 生成入口的 instructions 默认填充（一处、用户传入优先、AC-R1 回归保护）——侵入面在全部模块中最小。

## 四、上线门禁与排期建议

1. **本期上线决策（二选一，需产品拍板）**：
   - A. 隐藏 `/analytics` 入口（10 分钟改动，看板随二期上线）——**推荐**，代价最小；
   - B. 本期完成 DB1~DB5（8 人日）——价值是上线即有回采闭环，但挤占发布真实联调窗口。
2. 若选 B，开发顺序按 v1.1 §3：DB1 → DB2∥DB3 → DB4 → DB5；copy 注入最后做并跑 `smoke:copy` 回归（45 项全绿是 AC-R1 门禁）。
3. 无论 A/B：**`mocks/data.ts` 整文件删除**（P2-D3）都应做，防止后续新页面再引用假数据。

## 五、评审结论

现状无"开发缺陷"（模块未开工）；**原型资产质量高、可复用度约 70%**（骨架/图表/表格布局/口径文案与任务书一致）；上游锚点 10-28 复核全部成立；v1.1 文档（Q1~Q8 已拍板、契约已冻结）具备直接开工条件。唯一必须立即处理的是 P0-D1 的"无标注假数据"——在 DB4 或入口隐藏二者之间做决策前，不建议任何环境对最终用户开放该页。
